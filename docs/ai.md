# AI 协作规范：wiki → docs 迁移纪律

> 定位：`code/docs/` = 目标文档与权威定稿；`wiki/` = 现状与过程记录。两体系的分工、目录职责与归属裁决详规见 [README.md](README.md) 总纲，本文不重复。
> 本文只规定一件事：**什么时候、把一篇 wiki 文档迁到 docs 的哪里、怎么迁**。
>（docs 建设期（2026-09）的 12 条协作规则已完成使命，归档于 wiki `product/ai-collaboration-rules-archive.md`。）

## 一、何时迁（三条齐备才迁）

一篇 wiki 文档同时满足以下三条才迁，缺一不可：

1. **内容已稳定**：非过程稿、非草案，不再随工作高频回写；
2. **对应能力已实现**：协议规格类须代码已落地（规格描绘的是线上真实线形，不是设想）；
3. **属规范/说明书类**：回答"是什么 / 怎么做才对"，而非"发生了什么"。

**记录类永远不迁**：评审记录、排障案例、发版记录、测试/验收报告——它们回答"发生了什么"，永远归 wiki。

## 二、迁到哪

归属裁决按总纲 §三五条规则（内容主体决定归属；做什么 vs 怎么做；协议 vs 实现；规范 vs 记录；读者是谁）。边界不清时在文首用一行标注协作方，以主体所在区放置。

## 三、怎么迁（操作清单）

1. **复制**到目标区（保持或按区结构归位），不跨仓库 `git mv`（wiki 侧用 `git rm` 留删除记录）；
2. **修正内容**：过时状态标注、已被后续波次消解的段落、乱码行——只改这些，其余原样；
3. **链接改写**：docs 内部一律相对 `.md` 路径；指向留在 wiki 的篇目改文字形式（如 `` `org-claim`（历史档案，wiki protocol/org/） ``）；指向 wiki 其他区保留文字说明（如 `wiki architecture/sync/org-data-sync.md`）；
4. **wiki 原文删除**，并更新 wiki 侧所有引用：`_Sidebar.md`、各区 `README.md`、正文中的裸文件名链接（GitHub wiki 链接无路径无后缀，须 grep 找全）；
5. **更新 docs 侧索引**：目标区 `README.md` 补条目（每篇一句话说明）；
6. **两仓库各提交一次**（code 与 wiki 分开提交）。

## 四、红线

- **不留跳转空壳**：wiki 原文删除，不剩"已迁至…"的占位页；
- **不两边各存一份**：一处事实一处权威；
- **拿不准的不擅自迁**：归属或时机存疑的篇目，列清单一次性问用户，由用户拍板。
