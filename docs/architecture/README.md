# 架构设计文档（docs/architecture）

> 用途：**目标架构与迁移设计**——以 [../product/](../product/) 产品说明书为目标态，以 wiki 与代码为现状输入，产出"从现状到目标"的设计文档，供执行开发落地。
> 文档体系总体分工（docs = 目标/权威，wiki = 现状/记录）见 [../README.md](../README.md)。

冲突仲裁：产品语义以 `docs/product/` 为准；实现现状以 wiki / 代码为准；二者不一致在本目录"现状 → 差距"节如实呈现并给出迁移设计，不回改 product（product 变更只能经用户拍板）。

## 写作规则

1. **目录镜像** `../product/`：一篇产品文档对应一篇架构文档；对应多篇时建**同名文件夹**（如 `community/membership/`），文件夹内以 `_index.md` 做导航索引；
2. **统一模板**：产品目标（链接 product 篇）→ 现状（wiki / 代码核实，注明来源与核实日期）→ 差距 → 目标设计 → 迁移路径 → 验收（向量 / 测试要求）；
3. **先核实再设计**：动笔前必须读 wiki 对应规格与相关代码；不凭印象断言实现状态；
4. 协作纪律：先核实再断言、无来源标假设、不过度设计、诚实成色三档、一处事实一处权威（docs 建设期 12 条协作规则已归档 wiki `product/ai-collaboration-rules-archive.md`；[../ai.md](../ai.md) 现为 wiki→docs 迁移规范）。

## todo.md（工程排期）

工程排期 todo 是工作记录，已移至 wiki `architecture/todo.md`（**开发任务的唯一排期来源**），任务有两个合法来源：

1. **wiki `product/todo.md` 的 25 项**——需求权威，逐项回链编号；
2. **架构师差距分析**——product 文档写了、现状没做、但 product/todo 未覆盖的需求，回链 product 文档章节（以文档为准，不靠记忆）。

每项注明：目标架构文档、依赖关系、建议批次。完成后移出并更新对应架构文档状态。
