# 代码规范

> 本文档是星火（Spark）项目的代码规范，适用于仓库内全部源码。
> 基本原则只有一条：**结构合理、可读性强**。规范是手段不是目的——
> 当某条规则与可读性冲突时，以可读性为准，并在代码注释中说明理由。

## 一、基本原则

1. **结构合理优先于技巧**。能平铺就不嵌套，能直白就不炫技。三段相似的代码好过
   一个过早的抽象；抽象只在第三次重复出现时提取。
2. **可读性优先于行数**。命名说清意图，注释说清「为什么」。读代码的人（包括三个月
   后的你）是第一读者。
3. **最小改动**。修 bug 不顺手重构，加功能不顺手改名。一个提交只做一件事，
   diff 干净可审。
4. **一致性优先于个人偏好**。进入一个新文件，先读它的既有写法并保持一致；
   跨文件的同类代码遵循本文档的统一约定。

## 二、通用规范（与语言无关）

### 2.1 文件长度

- 单个源码文件**建议不超过 450 行**；**超过 650 行必须拆分**。
- 拆分方向按职责，不按字母：一个文件一个明确主题。参考现有做法：
  `core/src/org/service/` 按操作拆成 `create.rs`、`invites.rs` 等；
  `core/src/kernel/` 按域拆成 `org_ops.rs`、`message_ops.rs` 等。
- 测试文件可放宽（测试用例天然罗列），但单个测试文件超过 800 行时应按场景拆分。
- 配置文件、生成的锁文件不受此限。

### 2.2 命名

- **见名知意**：变量/函数名表达用途而非类型（`pending_requests` 而非 `list2`）。
  布尔量用 `is/has/can/should` 前缀。
- **作用域越大，名字越完整**：循环内 `i` 可以，跨函数传递的值必须全称。
- **缩写只用行业通用的**（`id`、`url`、`dto`、`ctx`），不自造缩写。
- 同类概念全仓库统一词汇，不混用同义词（如本项目统一用「空间 space」「会话
  conversation」「成员 member」，不再出现「域 realm」「聊天室 room」等变体）。

### 2.3 注释

- 文件头注释说明本文件职责与对齐的设计/协议章节（本项目惯例：注明对应的
  wiki 设计文档章节号）。
- 注释回答「为什么这么做」「为什么是这个值」，不复述代码在做什么。
- 代码改了，注释必须同步改——过期的注释比没有注释更糟。
- 用户可见的错误文案视为产品文案，集中管理、逐字稳定（测试可依赖）。

### 2.4 函数

- 一个函数做一件事，建议不超过 50 行；超过时先想能否按步骤拆分。
- 参数超过 4 个时改用结构体/对象传参。
- 早返回（early return）代替深层嵌套；嵌套不超过 3 层。

### 2.5 错误处理

- 错误分类清晰：用户可恢复的（给文案）、程序错误（给上下文）、外部失败
  （给原因）。不吞错误——必须忽略时写明理由。
- 跨层错误逐层转换，不穿透底层细节到 UI。

### 2.6 提交纪律

- 提交前跑通对应模块的测试与构建；不留红测试给别人。
- 提交信息说明「做了什么、为什么」，不堆文件名。
- 分支与合并策略见 §7。

## 三、Rust 规范（core / src-tauri）

### 3.1 分层与模块

- **纯逻辑层不碰网络与运行时**：业务模块（`org`、`contact`、`message`、
  `data_mgmt`）只操作 `StorageBackend`，时间一律 `now_ms: i64` 参数注入；
  网络只属于 `p2p` 模块；编排只属于 `kernel` 门面。
- 业务服务用**无状态结构体 + 静态方法**（如 `ContactService`），泛型
  `<S: StorageBackend>`，可单测、可替换存储。
- 模块入口 `mod.rs` 集中 `pub use`，外部只见门面不见内部文件结构。
- `pub` 最小化：能 `pub(crate)` 不 `pub`，能私有不 `pub(crate)`。

### 3.2 错误与类型

- 模块内错误用 `thiserror` 枚举，用户可见文案逐字稳定；`#[from]` 链接底层错误。
- 跨命令边界的类型定义在 `commands/dto.rs`，`#[serde(rename_all = "camelCase")]`
  对齐前端；core 领域类型不盲目派生 serde。
- 不用 `unwrap()`/`expect()` 处理可预见错误（测试与「不可能」断言除外，
  后者必须写明理由）。
- 不用字符串拼接构造存储键，统一走键构造函数（如 `conversation_key()`）。

### 3.3 并发与运行时

- Kernel 全部 API 同步；禁止在 tokio runtime 线程内调 Kernel（内部
  `Handle::block_on` 驱动 P2P）。跨线程共享用 `Arc<Mutex<_>>`，锁内不做阻塞 IO。
- 新增 P2P 协议照现有三段式：`begin_xxx`（发起）/ `handle_xxx_inbound`（应答）/
  `resolve_xxx`（汇总），业务回调经 `P2pHost` trait 注入，p2p 层不做业务落库。

### 3.4 命令层（src-tauri）

- 三层结构：`*_inner(&mut Kernel)`（可单测）→ `#[tauri::command]` 薄壳
  （只锁内核、转错误）→ `lib.rs` 按组注册。
- 命令返回 `Result<T, String>`，错误文案 = `KernelError` Display。
- 壳层测试用 tempdir 起真内核直调 inner，不 mock。

## 四、TypeScript / Vue 规范（app/src）

### 4.1 分层

- 页面/组件**不直接调 `invoke`**，一律走 `window.electronAPI.<域>.<方法>()`；
  域定义集中在 `src/api/types.ts`，channel 映射集中在 `src/api/command-map.ts`。
- 数据读写收敛在 store/模块方法上（如两个 `src/mock/*.ts` 接入层），组件不直接
  触碰存储细节——换实现只改收敛点。
- 跨页面通信用 `src/stores/pending-*.ts` 的请求-消费模式，不在组件间抛全局状态。

### 4.2 类型

- 跨进程边界的数据一律有 DTO 类型（`src/api/types.ts`），字段 camelCase，
  与 Rust dto 逐字段对齐；不用 `any` 跨越边界。
- 可选字段语义区分 `undefined`（未设置）与 `null`（明确清除），与后端约定一致。
- 字面量联合表达枚举（`'open' | 'chatOnly'`），不用裸字符串裸数字。

### 4.3 组件

- 组件只负责呈现与交互上报：数据经 props 进、经 emit 出；副作用收敛在
  store/组合式函数（如 `use-delete-contact.ts`）。
- `.vue` 文件建议不超过 500 行；超过时按区块拆子组件或抽组合式函数。
- 响应式状态的修改要可追溯：能走 store 方法就不在组件里直接改深层字段；
  必须直写时（如标签成员编辑）由 store 层兜底持久化并注明。

### 4.4 环境分支

- 非 Tauri 环境（vitest、纯前端预览）必须有明确降级行为，不能因为缺少
  `electronAPI` 而抛错；守卫集中在收敛点，不散落在组件里。

## 五、测试

- 测试体系与分层见 [测试体系](../testing/testing.md)：core 模块单测 + kernel 集成测试 +
  命令层真内核测试 + 前端 vitest。
- 新功能必配测试：纯逻辑测行为与边界（如撤回 2 分钟窗口的 ±1ms），
  集成测试测跨层链路（如双节点 dm 投递）。
- 测试不改产品行为来迁就；产品行为变了，先确认是需求变更再改测试。
- 测试命名说清场景与预期（`send_text_to_self_delivered_and_online`）。

## 六、协议与文档同步

- code 仓库 `docs/protocol/` 是字节级权威：**先改规格与 golden vectors，再改实现**；
  实现落地后规格必须回写到最新状态。
- 改了结构、约定、工作流，同步更新对应文档（wiki、TODO 清单、模块头注）。

## 七、分支与合并

> 目标：main 永远可构建、可测试、可发布；读 main 的提交历史就能读懂项目演进。

### 7.1 直接在 main 开发

同时满足以下全部条件时，可以直接提交到 main：

- 改动**小且独立**：文档/注释/文案、一行级配置、局部 bug 修复（不涉及跨层），
  一个提交能说清、能独立完成；
- 提交前本地对应测试与构建全绿；
- 不需要他人评审（无设计取舍、无对外契约变化）。

典型例子：修一个文案 typo、补一条测试、改 TODO 状态、修复一个已定位的单文件 bug。

### 7.2 切分支开发

满足以下**任一**条件，必须切分支：

- 新功能，或改动跨多个模块/跨层（内核 + 命令层 + 前端这类）；
- 工作需要多个提交推进，中途状态可能不绿；
- 改变对外契约（协议线形、命令接口、存储键）或引入新依赖；
- 试验性、探索性、可能被丢弃的改动；
- 需要他人评审的设计取舍。

分支命名：`<类型>/<简述>`，类型取 `feat / fix / refactor / docs / test / chore`，
如 `feat/dm-direct-protocol`、`fix/recall-window-boundary`。一个分支只做一件事。

### 7.3 合并

- **保持 main 线性历史**：分支合并一律用 squash merge（GitHub PR 的
  "Squash and merge"，或本地 `git merge --squash`），一个分支在 main 上落成
  一个语义完整的提交；禁止 merge commit 堆积，禁止对 main force push。
- 合并前自检（无论是否经过 PR）：
  1. 分支 rebase 到最新 main（`git rebase main`），冲突在分支上解决；
  2. 全量测试与构建绿（core / src-tauri / 前端 vitest + build，按改动面）；
  3. squash 后的提交信息说清「做了什么、为什么」，不堆文件名。
- 多人协作时合并走 PR + 至少一人评审；评审关注设计与契约，不做逐行格式洁癖
  （格式交给 §三/§四 规范与工具）。
- 分支生命周期以天计：开工即 rebase 勤快同步，合并后删除分支。
  超过一周未完的分支，先 rebase 落地一部分再继续，避免长期分叉。
- **hotfix**：线上/发布的紧急修复走 `fix/` 分支 + 快速评审；若改动极小且紧急，
  可按 §7.1 直接提交 main，但必须随后补测试。

### 7.4 提交信息

- 格式：`<类型>: <一句话说明>`（如 `feat: 消息与通讯录内核落地`、`fix: 撤回窗口边界判定`），
  类型同分支前缀；正文（可选）写动机与取舍，不复述 diff。
- 一个提交一个语义；不把不相关的改动混进同一提交。
