# 威胁面分析：自动密码统一触发（方案 a 前置评审）

> 类型：威胁面分析（新能力落地前）。
> 状态：**设计细化 v2 已按 §2.1 实现**（2026-08-31）；§3 威胁模型对 v2 依然成立
>（攻击面较蓝本更小：无新增网络信号、无对端输入信任），评审可对照实现终审。
> 关联：`m3-epoch-rotation-plan`（wiki architecture/identity/）、
> `sync-storm-fix` §Z.5.2（wiki architecture/sync/）（根因链）、
> `kernel/pw_ops.rs::password_unify_status` / `unify_password`（既有实现）。
> 背景日期：2026-08-30/31 真机双端联调实测。

## 1. 背景与要解决的问题

M3 epoch 体系下，ikey（数据密钥）的授予受 D′ 门控：接收方须以
`pwack:{peer}`（对 pwv 当前 V 的 MAC）证明口令知识。V = scrypt(口令,
**设备随机 salt**)——两台各自初始化的设备即使口令相同，V 也必然不同，
互验 MAC 永不过 → 门控常闭 → ikey 不授予 → epoch split-brain 永不愈合 →
该账号加密同步**永久退化为明文兜底**（功能正常，M3 加密目标失效）。

真机实测（§Z.5.2）：`recover_mnemonic` 第二设备登录后两端
`pw_grant_gated` 各触发 8+ 次，门控在观测窗口内未打开。

既有解法是**手动**密码统一（`password_unify_status` UI 已存在）：用户主动
发起后两端 V 收敛、门控放行。问题：触发条件（同账号 + 双端在线 + 口令
相同 + V 不同）用户不可感知，隐性故障会长期潜伏。

**方案 a（本评审对象）**：内核/壳层检测到上述条件后**自动发起** unify。

## 2. 方案 a 设计要点（评审蓝本）

1. **检测点**：解锁后 / 对端上线事件时比对本机 pwv 与对端宣告（hello 已
   携 epoch 宣告，可同通道携 pwv 指纹——如 `pwv.changedAt + salt 哈希`，
   不传 V 本体）。
2. **触发条件（四合一）**：同 rootId（自身份帧）∧ 双端在线 ∧ 本会话已
   解锁（口令在场）∧ 指纹不等。
3. **执行**：调用既有 `unify_password` 流程（新口令 = 当前会话口令），
   走既有轮换/扩散/回滚语义，不新增密码学原语。
4. **频率约束**：每对设备至多自动 unify 一次（成功后写标记
   `p2p:pw-unified:{peer}`）；失败后指数退避、上限 3 次转静默。

## 2.1 设计细化 v2（2026-08-31，实现前最终设计）

实现准备中发现**更优且攻击面更小的方案**，替代 §2 蓝本中的 hello 指纹信号：

- **不新增任何网络信号**（Q1 取消）：检测不需要对端宣告——pwv 本身经
  pdsync 同步，V 不同会在合入时天然置 `stale` 标记（既有
  `pw_verifier_mismatch` 路径）。
- **唯一判定**：会话持有的 Kverify 对**新合入的 V** 可解
  （`decrypt_with_kverify`，纯存储 + 已有会话秘密）。可解 ⟺ 会话口令
  即账号当前口令（V 由口令+salt 决定）——**密码学保证，无信任假设**。
- **Q3 时序守卫内生化**：真改密后 V 翻转，旧口令的 Kverify 解不开新 V
  → 不自愈。无需 changedAt 比较，无竞态窗口。
- **Q4 退避状态机消解**：操作要么成功（可解）要么不执行（不可解），
  逐信封自然重评估，无失败重试概念。幂等按 `changedAt` 粒度标记。
- **执行面**：复用 `unify_password` 的存储面语义（自锚 ack + 推进水位 +
  清 stale + 安全日志 + hello 补发旗标驱动 ikey 授予链闭合），同口令场景
  免身份文件重封（会话密钥仍有效）。
- **评审问题清单相应收敛**：Q1/Q3/Q4 不再需要拍板；Q2（UX 告知）默认
  取安全日志 + `PasswordUnificationDone` 既有事件外发（前端可选 toast）；
  Q5 不变。

## 3. 威胁建模

信任边界：配对自设备（同 rootId）已能互发 pdsync 全量（含密文）。unify
的净效果是**两端 V 收敛**——攻击者若能诱发不必要的 unify，造成的损害
是什么？逐项过：

### 3.1 攻击者能力假设

- A1：已配对自设备中的一台被攻破（拿到 root 签名私钥 + 在线）；
- A2：网络中间人（noise 通道已挡；假设其只能延迟/重放，不能解密/伪造）；
- A3：恶意 peer 伪装成同 rootId 设备（须过 dm 信封验签：from==my rootId
  且签名有效——即必须持有 root 私钥，能力等同 A1）。

### 3.2 攻击树与守卫

| 攻击路径 | 后果 | 现有/拟定守卫 | 残余风险 |
|---|---|---|---|
| A1 诱导对端与自己 unify | V 收敛到攻击者选定的值？unify 用**各自本地会话口令**重生成 V，攻击者无法指定 V 内容 | unify 不接收对端提供的 V（仅走 `unify_password(本地口令)` 重生成）；对端 MAC 验证仍按新 V 执行 | 低 |
| A1 在口令已变更未传播时诱导 unify | 旧口令设备被统一进旧 V？ | unify 的轮换语义（monotonic changedAt + 时间窗拒收）沿用既有防回滚守卫 | 低-中：**需确认 unify 与改密传播的先后语义**（已随 v2 消解，见 §2.1） |
| A2 重放旧 unify 触发帧 | 重复 unify（无害但费） | 成功标记 + 去重；unify 帧签名 + changedAt 单调 | 低 |
| A3 伪装设备触发 unify | 须 root 私钥；持有即已能读一切密文 | 无新增面 | 无新增 |
| 自动触发本身扩大攻击面？ | 新增一个「状态机入口」：伪造「V 不同」宣告诱导自动 unify | 宣告为只读信号；unify 的执行条件含本会话口令在场，攻击者无法替本机决定口令 | 低 |

### 3.3 与既有安全不变式的关系

- 密钥永不进同步流量：unify 只收敛 V，ikey 仍只走 dm 定向投递 ✓；
- D′ 门控语义不变：unify 后门控按新 V 重新校验 ✓；
- 防回滚（changedAt 单调 + 未来 ts 拒收）：沿用 ✓。

## 4. 不做自动触发的代价（评审需权衡）

维持手动 = 接受一个**可自动检测的长期明文兜底状态**——对「默认隐私隔离」
设计铁则的侵蚀是持续性的。实测中该状态无任何用户可见症状（同步正常）。

- **Q2 自动 unify 的 UX 告知**：静默自动 vs 一次性通知（「已自动统一设备间

- **Q5 发版门槛**：该能力是否进下一版，还是先以 ①(b) 强提示过渡一版？

## 6. 验收标准（实现后）

- 双端 V 不同场景：自动 unify 在解锁 + 对端在线后 ≤1 个 hello 周期内完成，
  随后 `epoch_key_granted` / `epoch_key_activated` 出现（门控放行）。
- 伪造宣告（篡改 salt 哈希）不触发 unify（负向用例）。
- 口令刚变更的窗口内不发起 unify（时序守卫用例）。
- 真机复验：§Z.5.2 的 `pw_grant_gated` 循环不再出现，加密类目走密文
  （流量审计无 profile:self 等明文）。
