# 组织形态配方：现实组织怎么落在 Spark 上

> 状态：定稿 ｜ 分册：第二层 · 共同体（横向指南）

## 一句话

Spark 不预制"家庭""公司""合作社""社区"这些形态——它提供一套零件（域、凭证、策略、事务、插件），本篇给出五种典型组织的**组装配方**：结构怎么搭、治理怎么声明、经济怎么配、边界在哪里。所有配方都只是**组织自己的选择**，不是内核的立场。

## 配方一：家庭（家庭数据中心）

- **结构**：家庭 = 叶组织（成员是个人）；每个人的个人空间仍是独立私域，不与家庭混同；
- **数据**：家庭共享数据（相册、文件、家庭账本）走家庭组织数据面，全家设备自动互备；个人数据仍只在自己的设备间同步——家庭共享与个人私域双轨并行（见 [personal-data](../foundation/personal-data.md)）；
- **家庭小主机 = 家庭数据中心**：一台常开的家用 PC / 小主机自动承担全家的数据节点与网关角色——手机上的组织数据只是暂存缓存，回家自动收敛、零丢失；家人的照片与文件随时可拉取。如同家里有一台 NAS，但没有 NAS 的配置负担，也不引入任何厂商云；
- **多人共用一台小主机**：每个家庭成员用自己的 OS 账号登录，各自运行自己的 Spark 实例、各自配对成"自己的设备"——小主机是全家共享的硬件，数据却每人各自隔离（OS 文件权限即边界）；
- **副本**：全家 PC 类设备（含小主机）合计达 K=3 即满足副本目标；只有手机的成员，引导自购第二台设备或借小主机补齐；
- **对外**：家庭作为"户"（组织成员）加入楼栋 / 小区——按户一票由共同体规则与户凭证表达（见 [model](model.md)）。

## 配方二：股份制有限公司

- **结构**：公司 = 共同体域；部门 / 子公司 = 子组织（独立数据边界），项目组 = 分组（纯标签）。要隔离就拆子组织，保密边界 = 域边界；
- **治理**：决策结构自由声明——老板独断、董事会 m-of-n 皆可（公示 + 延迟 + 留痕是底线）。**股权加权表决**：股权管理插件记录股本结构，按契约发布**股权快照**（插件签名 + 存证锚 + 时点），治理策略声明引用快照为票权权重——如同股东大会的"股权登记日"，以登记日名册为准开会（机制详见 [governance](../affairs/governance.md)）；第一版股权管理与策略可合并写成同一个插件（单插件闭环）；
- **经济**：法币经营在系统外（银行账户），Spark 不替法币结算、不管分红的钱怎么分；股权 / 分红 / 财报 = 插件记账（信息面）；内部激励可用积分（发行策略规则化：成交一单 → X 积分），但**内核经济对象（积分 / 债权 / 出资）不得作为票权输入**（三底线，见 [economy](../economy/README.md)）；
- **边界**：Spark 记录决议、不结算资本——"股权 → 票权"可接线，"股权 → 分红"永远在系统外。

## 配方三：合作社（Spark 的主场形态）

- **结构**：社 = 叶组织或共同体域；生产小组 = 分组或子组织；
- **治理**：集体决策模板（小组织默认"延迟生效 + 阈值否决"）；一人一票 / 按户一票由凭证声明；
- **经济**：积分劳动凭证全家桶——发行策略（评定规则可规则化）、兑付即销毁、公共账本 + 信息公示 + 签名表决（MVP 铁三角插件，见 [catalog](../plugins/catalog.md)）、不可分割储备与公共扣除（政策层规则包，见 [credits](../economy/credits.md)）；
- **边界**：不可分割储备管的是系统内积分侧；法币盈余的处置在系统外，靠合作社章程与法律（见 [fiat-compliance](../economy/fiat-compliance.md)）。

## 配方四：开源社区

- **结构**：社区 = 共同体域或叶组织；核心团队 = 分组；项目 = 公共议题（见 [public-topics](../affairs/public-topics.md)）；
- **治理**：参与阶梯（观察者 → 贡献者 → 投票者，贡献爬升），采纳即集体决策；上下文身份安静参与、公共身份积累公开履历；
- **经济**：规则化发行的最佳样本——发行策略写死"PR 合并 → X 积分、需求被采纳 → Y 积分"，触发事件来自事务日志（采纳本身就是集体决策），内核确定性执行，**不需要为每次发行开会**；积分用于社区内部资源（服务器、周边、活动），兑付即销毁。**Spark 自己的开发共同体就按这个配方运行**（自举，见 [roadmap](../roadmap.md)）；
- **边界**：没有"官方搜索结果"，indexer 可换；想被全网发现就把议题设为公开发布。

## 配方五：业委会（第一验证场景）

完整例子见 [model](model.md) 阳光小区与 [roadmap](../roadmap.md) 里程碑二，此处不重复。要点：按户一票由选举规则与户凭证表达（组织接受哪些成员类型由创世策略声明）；名册公示走开放授权；选举记名、全员可审计（法规要求）。

**结果交付街道办有三条路，按现实稳妥度排序**：

1. **打印 + 手工签字（默认，最经济也最稳妥）**：选举结果报告打印出来、相关人员手工签字，街道办按熟悉的纸质公文接收——零成本、零认知门槛，不依赖对方认可任何新技术；
2. **存证导出包（电子留档）**：导出包 + 独立核验工具，对方不装 Spark 也能验证签名与完整性（见 [evidence](../foundation/evidence.md)）——技术上最硬，但依赖街道办愿意接受并理解电子核验，现实中可能被一句"我们不认这个"挡回，宜作技术留档与备用核验；
3. **第三方电子合同平台（如法大大）**：走商业电子签渠道，法律效力清晰——但需要小区自己有公司 / 法人主体且按份付费，多数业委会没有主体、也不值得为此付费。

## 所有配方共享的底座

- **改规则必走事务**（公示 + 延迟 + 留痕），**用规则不走事务**（策略即自动机）；
- 资格跟着凭证走，验证人制度对接线下核验；原始材料不进组织数据；
- 数据归属不随加入关系上移；副本由全员 PC 承担，K=3 目标制；
- 插件是方法、组织是判断者；换插件不动数据，换客户端不动身份。
