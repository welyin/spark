# 成员、名册、副本与资格

> 状态：定稿 ｜ 分册：第二层 · 共同体
>
> 上游：`wiki/product/community-model.md` §七–十；`wiki/architecture/identity/organization.md`；`wiki/architecture/sync/org-data-sync.md`

## 一句话

这一篇管四件事：**怎么加入与退出、名册对谁可见到什么粒度、组织数据由谁的设备存几份、以及"你是不是真业主"这类资格由谁、用什么方式证明。**

## 一、加入：邀请人即引导节点

系统不设公共注册服务器，组织扩张沿真实信任链发生：

1. 管理员仅凭对方 RootID **预录**成员（对方无需在线）；
2. 生成一张有时效的**邀请码**（内含组织信息 + 邀请人节点地址）；
3. 被邀请人凭码**直连邀请人**，走点对点反熵链路完成加入；首次同步捎带自签名的地址凭证（公钥哈希即 RootID、带新鲜度、与连接地址比对防转述）。

首次加入上层共同体时引导"**以家庭名义加入**"，一人家庭即时成立——用户感知是一次确认，而不是"先建一个组织"。成员上线后认领自己被预录的条目；**退出**即成员资格凭证注销，其在共同体产生的历史按 [model](model.md) 的"退出留史"保留。

组织还可声明**免预录准入**：持有效凭证者自签即入册，无需管理员逐人预录、无需任何管理员在线——验证人的预先签名（线下已核验）加上组织的策略声明，替代了管理员的当场合签。

RootID 仅用于邀请定向与条目认领；**名册内呈现的是每域独立身份（org_user_id）**，跨域不可关联（承接 [identity](../foundation/identity.md)）。

## 二、名册开放：默认隔离，向上授权、可细到字段

"3 号楼的住户看不看得到 5 号楼的人？"——**默认看不到**，而且不是靠"不让你看"，是靠"数据根本不在你这一层"：楼栋名册留在楼栋域，小区层默认只有各成员组织的列表。**数据归属不随加入关系上移**——组织数据只属于它的托管域，上级共同体既不自动获得、也不自动保存下级的任何数据，除非下级显式授权开放。

**开放多少由成员组织自己授权，分三档：**

| 开放档位 | 共同体层名册里有什么 |
| --- | --- |
| 仅组织 | 只有各成员组织列表，无人员信息 |
| 代表可见 | 额外开放各组织代表（如"5 号楼楼长王五"） |
| 名册公开 | 额外开放全员名册（类比现实业主名册公示，业委会场景常为法规要求） |

共同体可以把开放档位**声明为加入条件**（如要求名册公示），但开放动作本身是下级组织的授权——接不接受条件、加不加入，是下级组织自己的选择；上级无权越取。

**互动身份**：在共同体事务里发言 / 投票时呈现什么身份，由事务规则决定——可实名到户号，也可匿名编号。内核不提供任何"标准姿势"：实名还是匿名是组织与事务规则（插件）的选择，法定场景该实名记票属事务规则层的判断，不在本篇。

此外还有**字段级授权**：昵称、户号、联系方式逐字段独立授权开放——**名册公开不等于手机号公开**；个人字段（手机号等）默认留在个人空间，进入组织名册须本人显式同意。更复杂的开放与可见规则由策略插件产出一份**声明式策略**、交内核策略引擎评估（不在读取点运行插件自有代码），并在保存策略时静态查出规则冲突与意外暴露面。

## 三、数据存在谁那里：托管域 × 公开发布

可见性不是一串等级，而是两个**正交属性**：

1. **托管域**：每个数据集合都托管在某个域、由该域成员节点复制保存。选托管域 = 选谁出存储、谁的成员默认可及。例如"业委会公开账本"托管在**小区层**：写权限仍属业委会，但存储与读取服务由共同体承担，住户无需加入业委会即可读取；
2. **公开发布（开关）**：任何托管集合都可额外打上"全网公开"标记、进入公共目录，任何节点无需凭证即可拉取。它与托管域不互斥——一份业委会决议可以既托管在小区层、又全网公开。

默认：数据集合托管在创建它的域、不公开发布。事务没有托管域（由关注者复制，见[事务模型](../affairs/affair-model.md)）。

## 四、组织数据副本：每层自足 + K=3 目标（按设备计数）

- **每层自足**：每层域的数据只由该层成员（个人或组织）的设备共同保存——家庭数据在家庭成员设备上，楼栋数据在各家庭节点上，小区数据在其成员组织（物业、业委会、各楼栋等）的节点上；任何一户设备离线，小区数据不受影响；上层不保存下级数据（即 §二的"数据归属不随加入关系上移"）；
- **全体成员 PC 都是数据节点**：组织里没有专门服务器、也没有"数据管理员"——全体成员的 **PC 类设备**自动承担数据服务（存副本、响应读取），手机叶子除外（不长期做种，承接 [network](../foundation/network.md)）；**个人成员的常在线设备同样可承担**，与设备属于组织还是个人无关。数据服务是**结构角色、不是权力角色**：与治理身份（管理员）解耦，任何角色都不天然握着组织的数据面；
- **副本按全副本设备计数（2026-09-10 修订）**：K 副本按"全副本设备"计数——副本本就是设备属性（底座层叶子 / 完整副本即按设备区分），设备属于组织还是个人不影响计数；**成员资格只是持有副本的前提**（域加密密钥随成员资格下发，非成员设备不能持有）。副本不足时按设备口径提示（"当前由 N 台全副本设备持有，需要更多成员设备上线"），原"待其他成员上线"的组织成员代理口径退役；
- **义务是集体口径 K=3**：全域全副本设备合计达到 **K=3** 即达成系统目标，不要求每台设备存全量——全员节点与 K=3 不冲突：节点多只是候选池大、服务面广，副本总量仍按集体口径封顶（若要求人人全量，副本义务才会随"一个组织加入多个共同体"乘法增长——那是本模型唯一真实的数据爆炸路径，由 K 集体口径封死）；
- **K=3 是目标而非保证**：副本健康度如实可见，不达标如实告知，系统不做强制处置；成员可主动多存感兴趣的数据、自然成为新数据源，实际副本数只会更高。对普通用户的体验应当**如同在用中心服务器**：照常发请求、拿到结果，底层从哪个 P2P 节点取由系统搞定，用户无感。

## 五、读取保护：读授权，而不是集合加密

- 共同体给成员签发**成员资格凭证**，住户凭它读取托管在共同体内的数据，无需逐个加入来源组织；
- 成员退出 → 凭证注销、**立即生效、零密钥轮换**；其退出前已合法下载的旧副本仍可本地读取——诚实承认"已发出的副本收不回"；
- **平台不做集合级加密**：保密边界 = 域边界，"不信任的节点就不要让它存数据"；类型级保密（如无记名投票的选票）由对应插件做端到端，平台只见密文；
- **历史保留由组织自治**：普通公告可约定 N 年后裁剪，决议、名册变更等关键数据默认不可裁剪；系统只负责向组织反映其成员节点的磁盘压力。被裁剪内容的哈希锚仍留在[存证链](../foundation/evidence.md)——能证明它存在过，只是不再持有内容。

## 六、资格证明：验证即插件，验证人才是信任

"你是不是真实业主"不由平台判断：

- **准入条件由组织声明**：接受哪些验证方式的组合（房产证人工核验 / 两户在册业主担保 / 政务实名接口……），不同共同体可以完全不同；
- **验证插件 = 可替换的方法**（收集材料、人脸核身、对接外部接口）；真正被信任的是有权签发凭证的**验证人身份**——换插件不动信任，换验证人才需要改策略；
- **产物是资格凭证**：验证人签名一条"身份 X 是小区 Y 的 3 栋 502 业主、核验方式 Z"。原始材料（房产证照片等）只给验证人看、不上链、不进组织数据；凭证只暴露资格结论（户号），不暴露姓名证件号——**证据最小披露**；
- **凭证生命周期**：不设有效期；资格变更（卖房、退租）由验证人主动注销；注销不抹历史，只失去此后的新操作资格；
- **一人多户**：两套房 = 两个家庭组织各持一户凭证，默认"一户一票"（两户两票）；若共同体规则要求"一人一票"，由验证人**可选地**附加"同人关联声明"合并计票——这会主动打破两户间的不可关联性，属 opt-in，仅在规则明确要求时启用；
- **租户等非业主居住者**：同样以组织加入、持**居住凭证**，可读组织数据、参与议事，但无业主大会表决权，租约结束凭证注销；同一户号下业主组织与租户组织可并存，权利各按凭证类型；
- **验证人失信、既往不咎**：组织撤销对某验证人的信任，不影响其已签发凭证的效力；确需变更的，按凭证注销 / 变更流程逐条发起；已被虚假凭证污染的表决，由组织按正常治理程序推翻重来（新事务引用旧事务申诉，见 [governance](../affairs/governance.md)）；
- 验证插件经手敏感材料，**强制开源（L1）可审计**；不设官方审核名单，信任判断交还给组织。

## 边界（这一层不做什么）

- 内核**不定义任何具体资格**（不判断谁是业主 / 居民 / 成员），只保证凭证可验、执行确定、过程透明；
- 不做跨组织身份追踪，跨域默认不可关联；
- 不强制每个成员全量存储，副本是集体 K 口径；
- 不做集合级加密、不做"退出即远程抹除"——退出失去的是此后的读取权，已合法获得的副本不追回。
