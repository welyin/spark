# 路线图：如何一步一步走到愿景

> 状态：定稿 ｜ 顶层分册
>
> 方向与终局见 [愿景](vision.md)，产品构成见 [产品全景](product-map.md)；本篇只讲**推进节奏与"先做什么、先不做什么"**。具体排期、批次与遗留事项以 `wiki/product/development_plan.md` 为事实源，本篇不写易漂移的工程数字。

## 一、三条排序原则

1. **先机器正确，再社会接受**：先让系统在自己身上被证明能可靠运转（自举），再去争取系统之外的现实机构承认（街道办）——所以自举排在业委会之前。
2. **组织内闭环优先，不依赖网络效应**：任何一层能力都先在**单个组织内**自洽成立，跨组织、网络化的能力是增量而不是前提。宁可小而完整，也不大而悬空（冷启动原则，经济系统 v1 同此原则）。
3. **先定规则，再做实现；每阶段有可判定的验收**：协议与产品规则先定稿，再写实现；一个阶段验收通过才进入下一阶段，不并行铺摊。

## 二、总览：七个阶段、两个验证里程碑

| 阶段 | 交付的产品能力 | 状态 |
|---|---|---|
| ① 协议规格 | 身份、同步、网络、组织、数据管理的规则先于代码确定，并以可复算的验收向量锁定 | 已完成 |
| ② 平台无关内核 | 与桌面 / 移动无关的统一核心，逐模块对规格验收；**经济内核（积分发行 / 兑付 / 恒等式）为本次重构新增，尚未实现，是里程碑一的前置** | 进行中 |
| ③ 桌面壳 | 桌面端可用，新旧实例可互连同步 | 已完成 |
| ④ 协作底座 + 插件终局形态 | 统一 DM 底座与通讯录数据作为内核能力落地（聊天应用为可替换插件）；插件沙箱、应用市场、分发与信任成型 | 已完成（内核机制） |
| ⑤ 移动壳 | 手机端可用（Android 先行、iOS 随后）；手机定位为**叶子**，不计入 K 副本，常驻副本由常开设备承担 | 进行中 |
| ⑥ **里程碑一 · Spark 自举** | Spark 的开发、发布、分发、反馈全部跑在 Spark 上 | 待启动 |
| ⑦ **里程碑二 · 小区自治** | 真实业委会完成一次真实投票，结果被街道办凭独立核验接受 | 待启动 |

> 阶段①–④是"把无字的机制做扎实"，阶段⑤补齐"人人都能参与"的设备前提，⑥⑦才是两场真正的验证。
>
> 状态口径说明：②的"进行中"指平台内核已完成、**经济内核待实现**；④的"已完成"指内核机制（沙箱 / 分发 / 信任）成型——插件间契约仍为设计草案，两个里程碑所需的业务插件均未开工（见 [catalog](plugins/catalog.md)），"终局形态"指架构形态而非生态就绪。

## 三、里程碑一：Spark 自举（阶段⑥）

**含义**：从指定版本起，Spark 自身的开发、打包、发布、分发、反馈闭环全部在 Spark 上完成（过渡期继续使用既有代码托管，不假装一夜切换）。

**为什么必须是第一个里程碑**：自己是自己最苛刻的第一个用户——团队每天用自家的事务、搜索与分发，设计缺陷按天暴露；附带收益是 Spark 自身成为公共议题平台上第一个真实存活的社区，上线即有真实内容。

**前置**：经济内核（阶段②的剩余部分）必须先于本里程碑实现——自举社区就是积分的第一个真实用户：开发贡献经集体评定记为积分、兑付即销毁，在 Spark 开发共同体内跑通组织内闭环。

**验收（全部满足才算达成）**：

- 源码在 Spark 网络上可获取与提交（项目仓库经内核文件同步分发为只读镜像，改动走 PR 子事务 + bundle/patch 附件，维护者本地合并后同步分发——无独立 Git 协议层，见 [公共议题](affairs/public-topics.md)）；
- 缺陷与建议以**事务**形式提交、讨论、形成决议（议题驱动开发）；
- 发布包经签名发布、包哈希进入存证链；
- 用户通过 Spark 网络（而非中心化发布页）收到版本更新；
- 运行反馈在 Spark 内提交并回流为开发事务；
- 开发贡献的积分发行 / 评定 / 兑付销毁在 Spark 开发共同体内闭环，发行恒等式可审计。

该里程碑所需基础插件见 [catalog 自举清单](plugins/catalog.md)；其中文件同步分发、签名发布是**内核能力**，Git 工具链（桌面 git CLI / 移动端 isomorphic-git 只读）随代码仓库应用插件提供，均不在基础插件清单内单列。

## 四、里程碑二：小区自治（阶段⑦）

**含义**：一个真实业委会用它走完「筹建 → 签名征集 → 投票 → 结果提交街道办」全流程，结果凭**离线独立核验**被接受。

- **MVP 铁三角 = 签名表决 + 公共账本 + 信息公示**，流程向导承担获客入口；所需插件见 [catalog 小区自治清单](plugins/catalog.md)；
- **技术桥梁**是[存证导出包 + 独立核验工具](foundation/evidence.md)：核验方不装 Spark、不联网也能验证签名与完整性——这是结果被现实机构接受的关键；
- 第一版选举采用**记名、全员可审计**——这不是产品倾向而是**法规要求**：业委会选举依法须实名签字、记票可追溯，产品没有第二种选择（Q09 已据此拍板）；无记名保密投票仅留给法规允许的其他场景，排远期；
- 落地前置：现场至少保障一台桥接 / 公网可达节点（Q04）、导出包附成员名册存证快照（Q05，已决前置）、副本健康度如实告知（Q06 已决：只告知不干涉，副本不足时如何补足由组织自行决定）。

**本里程碑的经济范围刻意收窄**：只做**单组织内**的积分发行 / 兑付 / 恒等式闭环与公共账本；跨组织双边受理、代理链、风险出清一律放到第五节 v2 之后，不挤进本里程碑（落实 open-questions Q13）。

## 五、能力分期：v1 / v2 / 远期

阶段是"工程推进轴"，v1 / v2 / 远期是"**能力成熟度轴**"。v1 能力支撑上述两个里程碑；v2 要等签约组织网络变稠密才有真实舞台，因此不提前复杂化。

### v1 · 最小闭环（单组织自洽 + 直接双边）

- **组织内**：贡献事实记录、集体评定事务、积分发行 / 持有 / 兑付销毁、发行恒等式审计；特殊生命周期（退社解耦、无继承、红冲走普通追加事务、时效）；兑付单最小状态机与最小供给声明（不做库存 / 档期 / 目录）；
- **实报实销**：在线两阶段核销，发行方不可达即失败，不做离线 / 赊账消费；
- **跨组织仅直接双边**：有受理协议即可跨消费，往来净额展示、净应收上限与到顶拦截、资源平仓登记、协议解除收尾；无直签即拒绝，不做长尾路径；
- **法币关系**：经营账与积分账分立、不挂汇率、不对私兑现；不可分割储备与公共扣除的最小记账。

### v2 · 网络稠密之后

- **代理受理链**：横跳 / 层跳双预算路径、免费的原子中转、成对零净往来账、中转权义对等开关；
- **有序出清原语**：状态冻结、按比例计算、全程存证（是否启动出清仍由组织决定，内核不代决）；
- 组织健康度与敞口看板（永久贡献档案与内部资本账户已删除：荣誉归插件视图、成员出资不设内核对象、不计息，见 [economy 总纲](economy/README.md) 三底线）；
- 占用攻击防护、层次聚合路由、兑付紧张确定性排队。

### 远期 · 不预研、不排期、不投入

- 经济：共同储备 / 互助保险实体化、街道级及以上跨共同体结算安排、新组织孵化基金治理；
- 平台：弱组织动态域、本地生活服务试点、完全开放的插件开发生态、跨域身份与数据互通。

> **政策层永远不做默认值**：贡献评定方法、积分刻度、储备比例、平仓折价、治理岗报酬倍数等一律由组织开源自定，社区模板库只收录"某组织的实践样本"，创建组织时必须显式选择或填写（机制与政策分离，见 [economy/README](economy/README.md)）。

## 六、明确"先不做"（防范围膨胀）

- **不做**全局共识公链、加密货币、匿名电子现金、中心化内容裁判与托管 SaaS（见 [vision 非目标](vision.md#三spark-不是什么明确的非目标)）；
- **不做**信用分 / 人品分，也**不做**随机陪审团式自动仲裁——贡献与履历只载可验证事实、由查阅者自行判断，争议只挂起、等组织自己的裁决凭证（与 [事务治理](affairs/governance.md)、[经济内核边界](economy/README.md)一致）；
- 不为稀疏网络里的长尾跨组织消费提前上代理链（v1 无直签即拒）；
- open-questions 中不阻塞前两个里程碑的悬置项（如无记名重密码学、个人域副本下限、设备与操作系统账号绑定）不拖慢主线，集中拍板；
- 中继、引导节点、骨干网关等**公共组件的供给**（由谁运行、如何收费）不属于系统本身：产品原则是"公共组件必须不可信化、可替换"，其临时供给方案在工程排期中解决，不进入内核。
