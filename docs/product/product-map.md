# Spark 产品全景（product-map）

> 本篇是整套产品文档的"地图"和术语权威：用一条主线、一张分层图讲清 Spark 的各部分如何咬合。读完本篇，再按需进入各分册。状态：定稿。

---

## 一、一条主线：物 → 人 → 事 → 价值

Spark 不是一堆功能的并列，而是四个逐层建立、缺一不可的层次：

```
┌─────────────────────────────────────────────────────────────┐
│ 第四层 economy  共同体经济                                       │
│   成果如何分配与交换：劳动凭证积分、双边互助清算、去资本化          │
│   （每一次发行/红冲的集体授权，都来自第三层的一个"事务"）          │
├─────────────────────────────────────────────────────────────┤
│ 第三层 affairs  事务：组织如何决策与行动                          │
│   事务是全局一等公民：集体决策、选举、表决、申诉、公共议题          │
│   （决策的"成员资格/凭证"由第二层提供；决议可反过来改组组织）       │
├─────────────────────────────────────────────────────────────┤
│ 第二层 community 共同体：人如何结成不集权的组织                   │
│   递归共同体 DAG、成员分个人/组织两类（类型门槛由创世策略声明）、    │
│   层级不产生权力、公示延迟禁令                                    │
│   （组织建立在第一层的身份、数据边界与 P2P 副本之上）              │
├─────────────────────────────────────────────────────────────┤
│ 第一层 foundation 底座：物归其主                                 │
│   个人/家庭数据同步与可靠保存、RootID 自证身份、P2P 网络、链式存证 │
│   —— 没有中心服务器，数据在你自己的设备上                         │
└─────────────────────────────────────────────────────────────┘
   正交轴 plugins：定义权去中心化、解释权下放给组织——贯穿四层每一处
              "这算什么 / 意味着什么 / 谁算合格"（见第五节）
   其余横切：① 链式存证与独立核验   ② 内核边界（机制 / 政策分离）
```

| 层 | 回答的根本问题 | 核心机制 | 分册 |
|---|---|---|---|
| foundation 底座 | 没有中心服务器，数据如何**属于我、可靠保存、能互通**（副本承诺分两级，见术语表） | 端到端加密同步、自证身份、P2P 直连 | [foundation/](foundation/) |
| community 共同体 | 人们如何**自愿结合，且结合不产生层级权力** | 递归共同体、叶组织、加入非吞并、禁环 | [community/](community/) |
| affairs 事务 | 组织如何**在阳光下**决策与行动 | 事务一等公民、公示延迟禁令、决议生效 | [affairs/](affairs/) |
| economy 经济 | 共同生产的成果如何**按劳动分配、互助交换而非资本增殖** | 劳动凭证积分、双边受理、风险有界化 | [economy/](economy/) |

> 四层"缺一不可"指**完整形态**，不是排期含义：v1 即包含四层的最小闭环——自举场景（开源社区）本身就需要事务决策与积分评定贡献；经济层 v1 只做组织内闭环，跨组织与网络化能力是增量而非前提（分期见 [roadmap.md](roadmap.md) §五）。

> **四层是"业务纵轴"，插件是正交的"定义轴"**：四层回答 Spark 能做什么，[plugins/](plugins/) 回答"谁有权定义这一切意味着什么"。内核不规定事务类型、资格标准、贡献算法、客户端形态——这些**解释**全部由开源插件给出、由组织自主选用。详见第五节。

## 二、层间如何咬合（最关键的接口）

分层不是切块各管各，Spark 的独特性恰恰在层与层的接口上：

1. **foundation → community（地基）**：共同体的"成员名册、数据边界、副本保存"全部建立在底座之上——域身份由 RootID 派生、跨域不可关联；每层组织的数据由其成员组织的设备共同保存（K 份副本），任何单机离线不丢数据。
2. **community → affairs（供给资格）**：组织提供"谁是成员、持什么凭证"的可验证事实；事务据此判断参与资格，但**资格跟着凭证走、不跟着层级拓扑走**。
3. **affairs → community（决议反向塑造组织）**：事务的决议可以直接产生组织效力——改组成员、换届、甚至从零创设一个组织；且组织必须**事先声明**"本域规则由某类事务决议决定"，决议才生效（防治理偷袭）。章程级变更必须公示、延迟生效、留痕（**公示延迟禁令**）。
4. **affairs → economy（经济的授权来源）**：积分的**每一次发行、红冲、争议处置**，其集体授权都来自一个决策事务；经济系统不另起炉灶建立第二套投票/决策机制。这是事务章独立存在的根本原因——它是治理与经济共同的发动机。
5. **economy → community（生产关系闭环）**：积分的兑付与跨组织互助，把成员与组织重新黏合成"各尽所能、按劳动凭证领取"的联合生产关系，而不是雇佣与按资分配。
6. **plugins → 每一层（提供解释）**：共同体凭什么认成员、事务按什么规则关闭与计票、经济如何评贡献与算汇率、用户用什么界面操作——这些"解释"都不是内核写死的，而是组织选用的开源插件给出的；插件可审计、可替换、可分叉，换插件不动任何数据。

## 三、横切四层的两个机制

### 3.1 链式存证与独立核验

关键状态（投票结果、财务/积分流水、决议、名册变更）形成只增不减的链式存证；配套**存证导出包 + 独立核验工具**：任何人不装 Spark、不联网也能离线验证签名与完整性。这是"街道办可接受电子投票结果"这类真实合规场景的前提，也是"无需信任运营方"的技术落点。

### 3.2 内核边界：机制与政策分离（全产品通用原则）

判据一句话：**只有存在"唯一正确答案"、可由密码学或确定性计算判定的事才归内核；凡需要理解内容、判断意图、权衡价值的事，内核最多提供透明证据，决定权在组织、插件或成员。** 三种手段——结构性强制（不设接口，物理做不到）、证据性支持（给确定性数据但不裁决）、不介入（纯治理过程）。完整论述见 [economy/README.md](economy/README.md)；该原则同样约束共同体与事务章的设计。

## 四、统一术语表

> 全目录用词以本表为准。

**身份与网络**
- **RootID**：由 Ed25519 公钥哈希派生的根身份，自认证、无平台账号；"身份即密钥"。
- **域身份 / 上下文身份**：从 RootID 按某个域或治理上下文派生的专属身份，跨域/跨事务不可关联。
- **设备信任**：多设备间的密钥授权与互为备份关系；丢设备/丢密钥的恢复建立在其上。
- **叶子模式**：移动端只消费、不对外提供副本服务的轻量工作模式；叶子设备上的组织数据只是暂存缓存。
- **数据副本的两级承诺**：个人数据只存于本人设备，可靠性靠设备信任与恢复机制（见 foundation/identity.md），单设备用户即为单副本，不承诺"永不丢"；**组织数据**才享有 K 副本承诺——由成员组织的设备共同保存（"组织即服务器"），任一单机离线或损坏不丢数据。
- **relay（中继）**：P2P 直连失败时的报文中转，是**协议外的普通服务**，可自由提供与收费，内核不审价。
- **orgq（跨组织网关邮箱）**：对方离线时的凭证事后送达队列，只用于送达通知，不用于"先成交后补单"。
- **链式存证 / 独立核验包**：关键状态只增不减地签名链接成链；导出后第三方不装 Spark、不联网即可用独立工具验证完整性与签名。

**共同体结构**（2026-09-10 修订：组织/共同体合并，详见 [community/model.md](community/model.md)）
- **个人空间**：纯私域，不是组织，数据仅自己可见。
- **组织**：唯一概念——成员分个人成员 / 组织成员两类，组织可嵌套（组织加入上层组织）；接受哪些成员类型由组织的创世策略声明（默认模板：叶组织＝仅个人、共同体＝仅组织，存量零迁移）。
- **递归共同体 DAG**：组织加入组织形成的有向无环图，一个组织可加入多个共同体，系统底层强制**禁环**。
- **加入非吞并 / 层级不产生权力**：加入上级不让渡、也不使上级自动获得本域内任何权力；数据边界原样保留。
- **计票权重是规则问题**：一人一票 / 按户一票 / 加权表决都由组织的规则与资格凭证表达，平台不预设。
- **公示延迟禁令**：任何章程级组织效力必须公示 N 天后才生效、全程留痕（时间以存证链为准）。决策结构（独断 / 多签 / 投票 / 延迟否决）由组织策略声明，内核只做确定性求值、不干预。底层不可变的是公示 + 延迟 + 留痕，不是决策结构。

**事务与治理**
- **事务 / 议题（affair）**：全局一等公民，**只有发起人、没有归属**；关注者持有副本，副本在则事务在，无人持有自然消亡（但产生过决议效力的结论锚定所在组织的存证链，效力永久可溯；事务本体的去留由组织自选保留策略，关注即保留）。
- **事务容器**：发起人 + 规则 + 签名操作日志 + 决议存证的最小骨架；具体类型由插件解释。
- **参与阶梯**：观察者 / 贡献者 / 投票者的默认门槛形态，状态从事务日志确定性推导，是上下文资格而非全局声望分。
- **公共身份 / 公开履历**：一个稳定公开账号及其可验证参与历史；只载可验证事实，不贴标签、不算人品分。
- **凭证 / 验证人**：凭证是"具备某资格"的签名结论（只载结论字段、最小披露）；验证人是有权签发凭证、被组织信任的角色——"验证插件是方法，验证人才是信任"：换方法（插件）不动信任，换验证人才需要改策略；验证人可被组织集体撤销，已发凭证按流程逐条注销（见 community/membership.md）。
- **决议效力**：事务达标自动形成决议，可改组/创设组织或变更规则，效力来源须组织事先声明。
- **申诉自指**：对决议的异议以"引用被争议事务的新事务"提出，走同一套集体决策，不设平行申诉机制。
- **indexer（索引者）**：订阅公共事务元数据、提供搜索与健康信号的节点，任何人可运行、可一键切换；匹配与健康信号都是内核确定性函数——健康信号即从事务日志复算的统计（活跃参与者趋势、采纳集中度、异议与被申诉次数、最近活动时间、分叉谱系），任何节点可复算，呈现方式由客户端竞争——排序不可被单一运营方操纵。

**经济**
- **积分（劳动凭证）**：组织对成员的资源兑付承诺，记名、只在本组织兑付、兑付即销毁，个人层不流通。
- **规则包**：组织经济规则的文本 + 开源插件引用 + 版本号 + 集体授权，是继身份/组织/事务之后的第四类一等对象。
- **双边受理**：两个组织约定"彼此成员可凭本组织积分在对方消费"，是相互受理而非货币兑换。
- **净额头寸 / 平仓**：双向消费抵消后剩余的组织间债权债务，定期以真实资源结清，不用法币、不展期。
- **代理受理链**：沿双边协议图多跳完成一次跨组织消费；信息沿链传递、信用不沿链传递，路径免费。
- **W—G—W / G—W—G′**：为买而卖（允许）与为卖而买、自行增殖（禁止）的区分，是全系统最高验收判据——用于新规则的上线审查（"它让 G—W—G′ 更容易还是更困难？"）；其可执行部分不靠内核识别意图，而由宪章层结构性不变量物理保证（无对私兑现接口、不计息、票权不读积分余额，见 economy/README.md）。

**插件与解释权**
- **定义权 / 解释权**：定义权指"一类事物是什么、按什么规则成立"的权力，Spark 不把它收在中心，而以开源插件去中心化；解释权指对具体语义（类型、资格、计分、呈现）的判定，下放给选用插件的组织。
- **插件（plugin）**：承载"解释"的可替换模块——事务类型、资格验证、经济规则包、应用视图都是插件；数据不属于插件，换插件不动数据。
- **安装通路信任级（L0/L1/L2）**：按"从哪条通路装上"分级——L0 侧载（仅能自核哈希、无仓库锚定）、L1 仓库锚定（源码公开可审计，主路径）、L2 官方签名（增强层）；**验证类插件安装必须 ≥ L1，L0 侧载直接拒装**；不设官方审核名单，信任判断交还给组织。
- **声明式策略引擎**：插件不在读取点执行自有判断，只产出声明式策略文档，由内核引擎评估并可在保存时静态查出冲突；名册可见性、向上开放、城门规则共用同一引擎（写时开放声明 + 读时城门，见 [membership](community/membership.md)）。

## 五、正交轴：插件——定义权去中心化与解释权下放

### 5.1 为什么这是权力问题，而不是功能扩展

传统软件由厂商独占"定义权"：什么叫有效投票、谁算合格成员、贡献怎么计分，都写死在中心程序里，用户只能接受。Spark 把这件事拆开：

- **内核**只保留机制（容器、状态机、防伪、恒等式——有唯一正确答案的部分）；
- **语义 / 解释**（这是什么类型、谁算合格、如何计分、用什么界面）全部由插件表达；
- **选择权在组织**：用哪个插件、信任哪个验证人，由组织自主决定并公开。

于是"定义权"从单一开发者去中心化到全网，"解释权"下放到每一个自愿共同体。这是 Spark 去中心化的另一半，分册见 [plugins/](plugins/)。

### 5.2 三方分工

| 角色 | 掌握什么 | 不能做什么 |
|---|---|---|
| **内核** | 机制与不变量（唯一正确答案） | 不写死任何类型、资格、计分与价值标准 |
| **插件** | 对语义的解释（类型/验证/规则/界面），开源可审计 | 改不了内核不变量；闭源插件不得执行资格与经济规则 |
| **组织** | 选用哪个解释、信任谁，并公开规则 | 选择即担责：坏解释的代价是无人签约的孤立，而非被平台封禁 |

### 5.3 四类解释对象贯穿四层

| 解释对象 | 回答的问题 | 主要服务层 |
|---|---|---|
| 事务类型插件 | 这是选举 / 预算 / 讨论？如何关闭、如何计票 | affairs |
| 资格验证插件 | 谁算合格成员 / 业主 / 参与者 | community、affairs |
| 经济规则包 | 如何评贡献、发行触发、汇率公式、取整方向 | economy |
| 应用 / 视图插件 | 用什么客户端操作、数据如何呈现 | 贯穿全层 |

### 5.4 解释权的约束（"下放"不等于"暗箱"）

- **三级公开**：规则文本、开源实现、可复算结果，缺一不可；
- **可替换、可分叉**：数据属于域 / 事务而非插件，换掉解释器，数据原样还在；
- **不可让渡边界**：防伪、状态机不回退、恒等式、公示延迟禁令的执行、确定性匹配——这些"唯一正确答案"插件无权解释，只能在内核给定的声明式边界内表达策略（与 §3.2 内核边界互为表里）。
