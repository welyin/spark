# 四类解释对象：插件到底在解释什么

> 状态：定稿 ｜ 分册：第五层 · 插件
>
> 上游：`wiki/architecture/community-affairs.md` §7.3（插件分工）。本篇只讲"类型与分工"，具体需要哪些插件见 [catalog.md](catalog.md)，本篇不登记清单。

内核提供无字机制，插件按"解释对象"分为四类，另有两类横切件。统一对照：

| 类型 | 解释的问题 | 产物形态 | 内核如何对待 | 开源要求 |
| --- | --- | --- | --- | --- |
| 事务类型插件 | 这是**什么事**、怎样算成立 / 关闭 | 内容结构 + 采纳 / 关闭规则 + 界面 | 提供事务容器与生命周期，按声明规则推进 | 规则可审 |
| 资格验证插件 | **你是谁 / 有没有资格** | 凭证（结论字段 + 签名） | 只验证凭证形式与签名，不重跑现实判断 | **强制源码公开** |
| 经济规则包插件 | 贡献怎么记、积分怎么发 / 兑 / 折算 | 声明式经济规则 | 内核按规则确定性落账、套算、守恒等式 | **闭源不得执行** |
| 应用视图插件 | 这件事**长什么样、怎么操作** | 界面与交互 | 只给数据域与挂载区域，可随时换 | 一般可审即可 |

## 1. 事务类型插件 —— 解释"这是什么事"

内核的事务是一个**无归属容器**（见[事务模型](../affairs/affair-model.md)），它不认识"提案、选举、申诉、报修、议题"中的任何一种。事务类型插件负责定义一类事务：

- 内容结构（需要哪些字段 / 材料）；
- 采纳标准（多少人、什么资格、什么阈值算成立）；
- 关闭规则模板（通过 / 否决 / 撤回 / 升级为申诉）；
- 呈现界面。

> 最小示例：表决事务——定义"选项、一人 / 一户计权方式、法定人数、通过阈值、公示期"；内核只负责把符合规则的签名 / 操作确定性地计数、锚定、存证。

## 2. 资格验证插件 —— 解释"你是谁、有没有资格"

负责准入与资格核验，通过人机流程**签发凭证**（如业主凭证、居住凭证）。它经手个人敏感材料，因此**强制源码公开可审计**，且：

- 凭证只放结论字段、最小披露，禁止姓名证件号；
- 插件没有"自行签发"的接口，签发必须走验证人的人机流程；
- 内核只验证凭证，**验证人才是信任源**；验证人可被组织集体撤销，已发凭证按流程逐条注销（见[成员与资格](../community/membership.md)）。

> 最小示例：业主资格核验——验证人核对现实材料后签发"某户号业主"凭证，选举事务凭此确认投票权，但系统并不掌握证件详情。

## 3. 经济规则包插件 —— 解释"价值怎么记"

承载[经济层](../economy/credits.md)的**政策层**：发行依据、贡献评定方法、兑付目录、定点刻度、两类积分分立、双边汇率公式、平仓周期与净应收额度等。它只产出**声明式规则**，由内核确定性执行落账：

- **闭源插件不得执行经济规则**（三级公开中的"规则实现公开"）；
- 规则包版本化、代际内冻结、存量不溯及；
- 内核守住的宪章层（恒等式、状态机、三底线、发行须依据经决议授权的发行策略）规则包无权改动。

> 最小示例：时间银行规则包（按服务时长计）、集体评议规则包（事实与评价分离、轮换回避）——都是可被组织显式选用或改写的**样本，不是默认值**。

## 4. 应用视图插件 —— 解释"长什么样、怎么操作"

论坛、公共账本、信息公示、任务看板、文档库等业务界面与交互，是最表层、最可替换的一类：

- 数据在内核与同步层、属于组织，视图只负责呈现与操作，换一个视图插件数据原样还在；
- 官方提供的论坛 / 议题客户端**只是参考实现**，不具特殊地位；
- 界面只能在壳层给定区域内渲染，无权伪装系统界面。

## 两类横切件

- **门槛插件**：解释"参与这件事需要满足什么条件"。账龄 / 参与阶梯这类能从**链上时间与操作日志确定性推导**的门槛必须由内核提供（插件伪造不了链上时间）；担保链、成本类门槛由插件产出凭证 / 证明，内核只验证产物。它是公共事务"验证唯一真实参与者而不暴露其身份"的防水军手段。
- **策略插件**：只产出**声明式策略文档**（开放三档、字段级授权、向上开放矩阵、城门规则），交内核求值器执行，自身**不在读取执行点运行代码**（见 [interpretation.md](interpretation.md)）。

此外，组织名片插件、议题客户端等属于视图 / 客户端形态；indexer（公共议题索引者）不是插件，而是"内核支持、任何人可自选启用"的节点角色。

## 插件之间：可监督、可组合，但不直接互通

- 插件默认互为数据孤岛，只能读写自身域（含文件对象——统一走内容寻址 blob 池，插件只见自己命名空间）；需要协作时，经内核中介调用对方**按契约公开的接口**，且一切调用逐次校验、永不直接打通数据；

### 组合：库包与构建期复用

把多个基础件组合成一个工作区（如「项目」插件），靠的不是把各插件的界面**拼**起来（沙箱孤岛，iframe 拼装只会得到一屋子互不相通的小窗户），而是**构建期代码复用**：

- **库包（library package）**：插件包的一种角色——可被依赖的代码库（UI 组件 / 领域逻辑 / schema 定义），不单独运行、**没有自己的数据域**；
- **构建期依赖 + 哈希锁定**：应用的 manifest 声明依赖的库，以**仓库地址 + commit / 哈希**为准（不以包注册中心的名为准——名字可抢注，URL 不可抢注），构建工具解析、核对后**全部打进安装包**（与"运行时禁止外部拉取代码"一致）；升级依赖是显式动作、留痕；
- **运行时仍是单实例沙箱**：组合应用是一个实例、统一渲染，不存在跨沙箱拼装；
- **数据域归组合者**：库是纯代码，数据写到组合它的应用的命名空间；跨应用的共享仍走契约接口 / 契约发布物（通道②，不变）；
- **供应链信任**：安装时展示完整依赖树（SBOM：每个库的仓库锚定 + 哈希），全部开源可审；
- 工具链双产物：同一源码工程既可打出**安装包**（给用户），也可打出**库包**（给其他插件作者，npm 包或 git 仓库引用即可，Spark 不自建包仓库）。
- **监督类插件不拿数据特权**：业务插件按约定暴露**只读接口**，监督插件聚合出"监督驾驶舱"；某业务插件没暴露接口，监督视图对应区域就显示"未启用"，优雅降级、不阻塞；
- 接口缺失 / 版本不兼容时消费方降级运行，不拖垮启动；不追求跨插件分布式事务。
- 契约接口的另一用途：为治理策略提供**可锚定的数据快照**（如股权、贡献记录）——插件签名 + 存证锚 + 时点，供策略声明引用为资格 / 权重输入（见 [governance](../affairs/governance.md)）；求值器只验证来源与完整性，不理解数据语义。
- > 状态说明：插件间契约为**设计草案、尚未实现**；第一版以单插件闭环为主。

## 边界（这一篇不做什么）

- 本篇不登记具体插件（在 catalog）、不写 SDK 与接口实现（在 wiki）；
- 任何一类插件都不能借"解释"之名改动宪章层不变量，或在执行点插入私有判定代码。
