# 运行时与信任：沙箱封能力，仓库即身份

> 状态：定稿 ｜ 分册：第五层 · 插件
>
> 上游：`wiki/architecture/plugins/plugin_system.md`、`plugin-runtime.md`、`plugin-data-api.md`、`wiki/protocol/plugin-dist`。本篇讲产品层面的隔离与信任，不讲 SDK / 协议实现。

## 一句话

Spark 无法保证第三方插件"心怀善意"，它保证的是：插件**作恶被关在沙箱里、规则源码可被审、判定结果可复算、随时可停用且数据不被绑架**。

## 双运行时：界面与常驻逻辑分开隔离

- **视图运行在独立沙箱里**：插件界面跑在与主程序**相互隔离的浏览上下文**中——支持进程隔离的平台上，插件卡死 / 崩溃只影响它自己的进程，主程序不被拖垮；本地存储按隔离边界天然分开；**禁止运行时从外部拉取代码**，所有依赖必须打进安装包，也默认没有任意外联能力；插件只能在主程序划定的区域内渲染，全屏 / 弹层一律由主程序代理，**防止插件伪装成系统界面**骗取操作。
- **常驻逻辑跑在内核内嵌的轻量脚本沙箱中**：监听消息、定时任务、长连接等无界面逻辑不依赖界面存在，由内核为每个启用的插件拉起**独立沙箱实例**，并强制资源上限（内存 / 栈 / 单次执行时长），超时可被强制中断、死循环也能被停机；脚本异常只终止该插件自身。内核并不认识 AI、机器人等任何具体业务，脚本引擎对它而言只是和网络栈同级的通用基础设施。
- **一插件一实例、按容器隔离**：同一个插件在个人空间与不同组织里是**完全独立的实例**，数据、身份、权限互不相通。

## 能力最小化

- 插件**只能通过标准能力接口**使用系统功能，并在安装包中**事先声明**所需能力；
- 每次调用都经过三重过滤：**已授权 ∩ 当前视图允许 ∩ 当前空间允许**；调用方身份（哪个插件 × 哪种视图 × 哪个空间）由主程序绑定，**插件自报不作数**；
- **私钥永不离开内核**：需要签名时由内核代签，插件与界面层拿不到任何私钥；
- **隐私红线**：插件读不到他人的人际会话，只能读写自己的应用会话与自身数据域；高危能力（动用身份签名、读取通讯录）首次使用时单独弹确认，这份名单刻意保持很短；
- **文件与命名空间隔离**：插件不直接接触操作系统文件系统——文件统一走内核的内容寻址 blob 池（与附件 / 大文件同一套分块、同步与配额），插件只能读写**自己命名空间**下的对象；跨插件的文件访问只有一条路：对方按契约公开的接口；
- 能力可被用户 / 管理员随时收回，停用即切断能力、数据保留。

## 熔断与可恢复

- 心跳看门狗定期探活，连续无响应可一键关闭该实例；
- 崩溃环自动停用：短时间内反复崩溃 / 无响应即自动停用该容器内实例、入口置灰，可手动重新启用；插件自行上报的错误**只计数、不参与自动停用**（防止恶意插件靠谎报错误自我拒绝服务）；
- 主程序是无状态的壳，会话、草稿、数据都在内核持久化，即使渲染进程整体被杀，重启损失接近零。

## 可达性不依赖"对方装没装插件"

应用 / 公告消息**强制携带纯文本摘要**：装了对应插件就富渲染，没装则主程序原生展示摘要。于是组织公告等场景**全员可达**——数据先于插件代码同步到成员设备，不会因为某人没装插件就收不到组织的正式信息。

## 分发与信任：开源仓库即插件身份

Spark 没有中心应用审核，信任锚定方式与传统应用商店根本不同：

- **插件身份 = 规范化的开源仓库地址**，全局唯一、人类可读、点开即可审代码，"抢注名字"在物理上不成立（URL 无法抢注），显示名只是提示；
- **仓库的写权限就是签名能力**：谁能向该仓库推代码、发版本，谁才能签发这个插件——托管平台的账号与二次验证体系就是密钥管理设施，开发者无需自管签名私钥；信任一个插件 = 信任该仓库的全体维护者；后续升级信任同一仓库的连续性；
- **安装包内的自我声明不算数**：恶意广播者可以打一个"自称来自某仓库"的包。真正的锚是"内容**确实来自身份所指的仓库**"：展示 / 安装前从该仓库取回声明文件核对，不一致即拒；
- **市场只是广播索引**：它不可信、也不需要可信，只负责让插件被看见；"探索"页对已验证条目**随机排序**（每次刷新洗牌，没有稳定位置就没有可收买的排名位），搜索始终精确直达，举报只影响排序、不影响可达；
- **镜像只是通路**：经第三方镜像 / 代理获取时，包哈希必验、可多镜像交叉比对，官方 / 高价值插件可额外挂数字签名；镜像最坏只可能让你"下不到"，不可能让你"下到假的"；最稳的是原生多托管（同时挂多个代码托管平台）；
- **市场界面也是可替换应用**：默认内置一个市场前端，任何人可以做自己的市场——但签名验签、信任级判定、仓库锚定永远在内核 / 协议层，不由市场插件代行（信任根不可外包）；
- 也支持**手动侧载**安装包（网络差时），界面显示哈希供人工核对。

### 安装通路信任级 L0 / L1 / L2

同一个插件"从哪条通路装上"决定其信任级。它分级的是**安装来源**，不是插件的"敏感度"，也不要求作者自管签名私钥：

| 级别 | 安装通路 | 可信程度 |
| --- | --- | --- |
| **L0** | 侧载（手动导入）/ 旧记录缺省 | 只能自行核对整包哈希，**没有源码仓库锚定** |
| **L1** | 仓库锚定（主路径） | 内容确来自插件 id 所指的开源仓库，源码公开可审计 |
| **L2** | 官方签名 | 在 L1 之上额外带官方数字签名链，属增强层、非生态门槛 |

> **硬规则：验证类插件（经手个人敏感资格材料）的安装信任级必须 ≥ L1，否则拒绝安装。** 也就是不允许用一个 L0 侧载、来路不明的包去承担资格验证；L1、L2 均可。（工程侧以"插件声明了资格凭证相关能力"作为验证类的最小判定信号，产品侧以"经手敏感材料"为准。）

## 开源义务与垃圾防线

- **承担资格验证、经济规则、治理判定的插件必须源码公开可审计**；验证类插件因经手敏感材料，强制达到"源码公开可审计"这一档；不设官方审核白名单，信任判断交给用户与组织；
- 广播发布以工作量证明抬高单条成本、以中继资历制压制批量马甲、以消费侧懒惰核查让垃圾"无注意力收益"、以有效期让死插件自然淡出——没有审核，但洪泛在协议层被压到极低速率。
- **平台限制（如实标注）**：iOS 受应用商店规则限制，动态加载插件降级为"审核后随版本内置"；安卓与桌面不受此限。

## 边界（这一篇不做什么）

- 不为第三方插件的"善意 / 质量"背书，不设中心审核与官方白名单；
- 不允许插件突破沙箱、触碰私钥、跨容器读数据或在判定执行点运行私有代码；
- 工程实现（沙箱选型、桥协议、能力清单、打包格式、广播协议）见 wiki，不进产品说明书。
