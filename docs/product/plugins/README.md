# 第五层 · 插件（Plugins）：把定义权去中心化，把解释权下放给组织

> 状态：定稿
>
> 这一层与前四层（物 / 人 / 事 / 价值）**正交**：前四层提供无业务含义的机制，插件决定每一个具体组织"这些机制按什么规则成立"。
>
> **术语说明**：同一事物在三个语域的名字——docs 产品文档统一称「**插件**」；UI 与面向最终用户的用户手册称「**应用**」；面向开发者的材料以「**插件与应用开发**」并提（让开发者第一眼建立映射：用户看到的是应用，你开发的是插件），其正文技术内容沿用 plugin / pluginId。**应用是插件的实例**——用户安装、使用的业务单元，以插件机制运行；不是两个概念。

## 一句话

插件不是一个"功能市场"，而是 Spark 的**解释权装置**：传统平台把"什么算有效投票、谁有资格、贡献怎么计分、内容长什么样"的**定义权和解释权独占在平台方手里**（黑箱、可单方面改规则）；Spark 反过来——内核不含任何业务逻辑，这些规则全部以**开源插件 / 声明式规则**的形式存在，由**每个组织自己选用、自己立法、可审计、可替换**。Spark 因此把定义权去中心化，把解释权下放到了组织。

## 三条命题

1. **内核无业务**：一切业务（论坛、投票、账本、公示、积分规则……）都是插件——连聊天应用本身也是（默认内置、可替换）；内核不认识"业委会""表决""工分"这些概念，只提供身份、事务容器、凭证、数据集合、积分状态机、存证与同步、DM 底座与通讯录数据这些**无字的机制**。
2. **解释权下放且可审计**：一个组织启用某套插件，就是在为自己"立法"——这套规则的源码必须可审，成员看得到"我到底受什么规则约束"；不设官方审核白名单，信任判断交给选用它的人 / 组织。
3. **解释结果可复现**：凡是需要"判定"的环节，插件只能产出**声明式规则**或**凭证产物**，由内核确定性求值 / 验证，而不能在判定执行点运行一段自有黑箱代码给出无法复算的结论。同一规则在任何成员的设备上必然得到同一结果——这是集体决策、存证与跨组织清算成立的前提。

## 不可让渡的边界

解释权下放不是无限授权，有四条线插件永远不能越过（对应前四层的宪章层不变量）：

- **关不掉的不变量**：公示延迟禁令、经济三底线、积分状态机与防伪、删除 / 红冲规则，插件无权关闭或绕过；
- **执行点不跑私有代码**：成员城门验证、资格判定、经济计算等"判定时刻"由内核按声明式规则求值，插件不得在此插入自有逻辑；
- **闭源不得承担规则判定**：执行经济规则、资格验证、治理判定的插件必须源码公开可审计；
- **能力被沙箱封死**：插件拿不到任何私钥、读不到他人人际会话、跨不出自己的容器与数据域。

## 与其他层的关系

插件是正交轴，不改变、只**解释**前四层：

- 对[共同体层](../community/model.md)：谁是成员、什么资格可见，由**资格验证 / 策略插件**解释；
- 对[事务层](../affairs/affair-model.md)：这是哪一类事务、怎样算通过，由**事务类型插件**解释；
- 对[经济层](../economy/README.md)：贡献怎么记、积分怎么发兑、汇率怎么算，由**经济规则包插件**解释；
- 对[底座层](../foundation/personal-data.md)：数据怎么呈现、做成什么应用，由**应用视图插件**解释；而同步、存证、身份、网络这些机制本身不是插件、不可替换。
