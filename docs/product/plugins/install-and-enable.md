# 安装与启用：一份代码，按空间实例化，规则类由组织立法

> 状态：草稿 v0.1（待评审）｜ 分册：第五层 · 插件
>
> 本篇收拢一个常被"安装插件"一个词糊住的问题：**代码谁都能拿，但"在哪个空间生效、谁有权启用、启用后怎么在组织内一致同步"是另一回事。** 机制上游见 [runtime-and-trust.md](runtime-and-trust.md)、[interpretation.md](interpretation.md)、[plugin-types.md](plugin-types.md)，本篇只讲权责与作用域，不讲 SDK / 分发协议实现。

## 一句话

**应用人人可装到本机；在个人空间自主启用，在组织空间由组织启用（规则类须走立法程序）；插件不分"个人版 / 组织版"，同一份代码挂到不同空间就是互相隔离的实例；他人不装也收得到、看得懂摘要，只有看富详情和动手操作才需要对应插件，而规则的效力由内核保证、与装没装无关。**

---

## 一、先拆"安装"：它是三个动作

"安装插件"同时指了三件权责不同的事，必须分开：

| 动作 | 是什么 | 谁的动作 | 关键约束 |
|---|---|---|---|
| **① 拿到代码** | 把插件包下载 / 侧载到本机 | 个人，自由 | 插件身份＝规范化开源仓库地址（pluginId），市场只是广播索引、无中心审核；信任级 L0/L1/L2 见 [runtime-and-trust](runtime-and-trust.md)。**下载到本机 ≠ 任何空间启用了它** |
| **② 在某空间启用** | 把插件挂到一个具体空间、实例化运行 | 个人空间＝个人；组织空间＝组织（见第二节） | 作用域永远是**单个空间**，不存在"全局启用" |
| **③ 运行实例** | 该空间里真正跑起来的沙箱实例 | 内核按容器拉起 | **一插件一实例、按容器隔离**：同一插件在个人空间与不同组织里是完全独立的实例，数据 / 身份 / 权限互不相通 |

> 典型例子是通讯录：个人空间里的实例管个人好友，组织空间里的实例管组织成员——两套人脉是**同一份插件代码的两个隔离实例**，不是两个插件。

### 形式化定义（2026-09-10 拍板补充）

两组概念的正交定义，任何 UI / 协议设计都按此对齐：

- **安装 / 卸载（系统层，代码管理）**：只回答"这台设备上有没有这份代码"。本机动作、个人自由、无空间守卫；卸载只移出本机、不删数据、不存在"组织卸载"。
- **启用 / 停用（空间层，逻辑成员关系）**：只回答"这个空间认不认这个应用"——是**纯逻辑状态，不要求代码在场**。启用一个不存在的应用合法且常见（组织场景：组织先决议启用，成员设备后按需获取代码）。启用状态属于空间治理状态（组织启用清单走组织副本同步），代码属于设备。
- **打开 / 运行（实例化）**：唯一真正需要代码在场的时刻。启用但未安装的应用可以出现在空间的桌面 / 启动器里；**用户试图打开时才提示"还没安装到本机"并就地安装**（含权限确认），装完即用——代码按需获取由此闭环，空间的逻辑构成（启用了什么）与设备的物理状态（装了什么）互不阻塞。

推论：**"先启用、后安装"是唯一合法顺序**——启用是决策，安装是决策的延迟兑现；不存在"必须先装才能启用"的约束。

## 二、谁决定启用：空间 × 插件性质

启用权不看"谁想要"，只看**在哪个空间、是不是规则类**：

| 空间 | 插件性质 | 谁拍板启用 / 更换 |
|---|---|---|
| **个人空间** | 任意 | **个人自己**，装、卸、换随意，只影响本人 |
| **组织空间** | **规则 / 立法类**：事务类型、资格验证、经济规则包、治理 / 策略 | **必须走组织事务、集体决议**；管理员也不能私装私换 |
| **组织空间** | **纯视图 / 工具类**：看板皮肤、只读视图、个人偏好 | 组织策略自定：可统一装，也可放权成员本地自选 |
| **组织空间** | 默认内置件（聊天 / 文件 / 通讯录 / 组织管理 / 应用市场） | 组织成立即具备，**更换**才走决议 |

两条必须连带成立的推论：

1. **规则类随组织强制一致，不能各装各的。** 计票、积分要在任何成员设备上算出同一结果，参与治理就必须认同一套已立法规则。成员不认可可以退出组织，但不能在本地让"我的票 / 我的账按另一套规则算"。**视图类恰好相反**：数据属于组织、存在内核，换一个视图插件数据原样还在，成员可自由换。
2. **启用 / 更换规则类＝组织立法。** 采纳与更换本身要走组织自己的决策程序，规则代际化、代际内冻结、升级＝启用新一代、旧规则不溯及既往（详见 [interpretation](interpretation.md) §规则即立法）。

## 三、插件不分"个人版 / 组织版"

**不做两套插件分类，只做"一份代码 ＋ 按空间隔离的实例"，再用能力声明自然区分适用域。**

1. 运行时本就按容器隔离，个人空间与组织空间是不同容器，机制上已经分开，再立两套分类是重复造概念；
2. 大量插件两边都要用（文件、相册、论坛、看板、AI 助手）：同一份代码、各自隔离的数据与实例；
3. 真正区分适用域的是**它需要什么能力**。插件在 manifest 里事先声明所需能力，每次调用都过"已授权 ∩ 当前视图允许 ∩ **当前空间允许**"三重过滤（见 [runtime-and-trust](runtime-and-trust.md)），于是：
   - 需要**读成员名册 / 发起集体事务 / 发行积分 / 签发资格凭证**的插件，这些能力只有组织域才提供，个人空间里不存在 → 自然无法在个人空间启用，不必人工贴"组织插件"标签；
   - 纯个人工具（日记、个人 AI、个人动态）不申请这些能力，只在个人空间出现；
   - 中立件（文件、通用视图）两边能力都满足，两边都能启用。

四类解释对象的**典型适用域**（类型定义见 [plugin-types](plugin-types.md)）：

| 类型 | 典型适用域 | 原因 |
|---|---|---|
| 事务类型插件 | 组织域为主 | 解释"集体如何共同决定"，个人空间没有第二人，不构成集体事务 |
| 资格验证插件 | 组织域 | 验证"你是不是成员 / 有没有资格"，个人无须自证 |
| 经济规则包插件 | 组织域 | 积分由组织发行，个人不发行对他人的分配 |
| 应用视图插件 | 个人域与组织域 | 同一份界面程序，挂不同空间即不同实例 |
| 门槛 / 策略（横切） | 组织域 | 服务于集体参与门槛与开放策略 |

> 这是"典型"而非"封禁"：适用域由能力与机制自然约束，内核不维护一张人为的"个人 / 组织插件"名单。

## 四、可达性分层：不装也收得到，详情才需插件

"要看是不是就得先装插件"是错的。呈现分两层：

- **摘要 / 列表层——不装也能看。** 应用 / 公告消息**强制携带纯文本摘要**；事务列表的标题、所属域、类型、状态、进度、倒计时等**容器级元数据由外壳原生渲染**。没装对应插件的成员，消息里看得到纯文本、列表里看得到这条事；
- **富详情 / 操作层——才需要对应插件。** 想看这类事务的完整形态、去投票 / 兑付，才打开对应类型插件；没装则给"去应用市场安装对应程序"的空状态（如同系统没有能打开某类文件的程序）。

**效力 ≠ 呈现。** 规则如何计票、如何落账，由**内核按组织已立法的规则确定性求值**，不依赖每个成员装没装那个插件的代码；不会因为某人没装，决议就对他不成立——他只是没有富界面，结果照样约束他。这就是全员可达底线：组织的正式信息与规则效力，永远不能被"你没装某个插件"挡住（数据先于代码同步）。

一次表决的完整闭环：

1. 发起人在组织空间用「签名表决」插件发起 → 生成一个表决事务（无归属容器 ＋ 类型标识），并向全体成员的应用会话投递卡片；
2. 成员 A 装了插件：列表看进度 → 点进去富界面投票；
3. 成员 B 没装：列表照样看到标题 / 状态 / 倒计时，消息里看到纯文本"X 议案将于…表决"，点详情才被引导安装；
4. 无论 B 装没装，计票由内核按同一套规则算出，结果对 B 同样有效。

## 五、组织"启用了什么"如何在组织内同步

组织启用了哪些插件、哪一版、担任何种角色，是**组织治理状态的一部分，必须在组织内同步**——否则成员设备不知道受什么规则约束，本地内核也无法求值与复现（对应三级公开第一条：成员加入前即可见启用了哪套规则、参数是什么）。但要分清同步的三样东西：

| 同步内容 | 走不走组织加密副本 | 要点 |
|---|---|---|
| **① 启用清单**：pluginId、版本锚点、承担角色、经哪条事务启用 / 更换 | **必须走，全体一致** | 变更本身走事务、存证、**代际化**；历史代际也要留存，老事务按它成立时那代规则复算 |
| **② 声明式规则 / 策略文档**：阈值、开放档位、字段授权、积分发行参数等 | **必须走，到每台设备** | 本地内核据此求值；文档**按哈希自认证**，改一个字节即失配、拒执行 |
| **③ 插件代码本身** | **不走组织副本** | 代码全网同一份、与具体组织无关；设备按清单里的 pluginId＋版本锚点，从开源仓库 / 市场 / 镜像或 P2P **按需获取、哈希验真**（L1 仓库锚定），不在每个组织的加密副本里各存一份 |

补充规则：

- **本地私改无效。** 某成员在本机私自改启用集或规则，只会与经决议同步下来的集合对不上、被求值 / 验证拒绝；权威来源只有"最近一次合法决议确定的启用集"；
- **清单内区分两种效力。** 规则类＝强制一致；视图类登记为"组织默认 / 推荐"，成员可用自己的视图替代；
- **加入前可见。** 启用清单与规则文本对成员、对考虑加入者可见，这是他判断是否认同规则、是否加入的前提。

## 六、边界（这一篇不做什么）

- 不重复沙箱、双运行时、熔断、能力清单与 L0/L1/L2 信任级（在 [runtime-and-trust](runtime-and-trust.md)）；不重复四类解释对象与横切件（在 [plugin-types](plugin-types.md)）；不登记具体插件清单（在 [catalog.md](catalog.md)）；
- 不写 SDK、打包格式、分发 / 广播协议实现（在 wiki）；
- 内核不替组织判断"选得公不公平 / 好不好"，只保证：启用经合法组织程序、规则确定可复现、变更留痕可追、代码可验真、停用不绑架数据。
