# 个人数据：一个人的多设备，一份一致的数据

> 状态：定稿 ｜ 分册：第一层 · 底座
>
> 上游实现：`wiki/architecture/sync/personal-data-sync*.md`、`docs/protocol/data-mgmt.md`

## 一句话

以你的根身份为界，你名下的**全部数据**在你登录过的所有设备之间做"全量备份式"自动同步——离线随便改，上线自动合并，最终所有设备内容一致。"个人空间 / 组织空间"只是界面分区，不是数据归属的分界：你在各组织里看到的内容，其个人侧副本同样属于你的个人域、同样在你的设备间同步。

## 为什么是"一套统一同步"，而不是每个功能各同步各的

早期每一类数据（联系人、会话、组织资料……）各自实现同步，暴露出三类用户能直接感知的毛病：换设备后内容不全；在一台设备删掉的联系人会在下次同步时悄然"复活"；不同数据的冲突处理口径不一致。

因此同步被下沉为底座的统一能力：**任何一类个人数据都天然获得多设备一致、删除可传播、离线可合并**，以后新增功能不必再重造一遍同步。

## 核心规则

### 1. 个人域内完全互信

- 个人域 = 同一个根身份名下、已完成配对的全部设备；
- 域内设备**完全互信**：一台设备一旦配对，即被授予读取全部个人域数据的权限，不做事中分级。这意味着"配对"是一个高信任动作（见[边界](#边界这一层不做什么)）。

### 2. 两条正交通道，隐私互不串线

- **个人同步**只在你自己的设备之间直连加密传输，**不经过、不停留**在任何组织成员或其他节点上；
- **组织同步**在组织成员之间进行，承载组织域数据。
- 两条通道正交：个人数据永不混入组织流量，反之亦然。

### 3. 离线可写、最终一致

- 任何设备离线时都能正常读写；重新上线后自动与其他设备做差异对账，互相补齐缺失部分；
- 同一条记录在两台设备上被同时改动（真冲突）时，以时间更新者为准：后到覆盖先到——另一台设备几乎同时的修改会被覆盖掉，这是最终一致的固有代价，换来所有设备无需手工合并即收敛到同一结果。已知边界：设备时钟明显不准时会带偏"谁后到"的判断。

### 4. 删除是一条必须送达的"事实"

- 删除会同步到你的每一台设备，并且**不会复活**（系统为删除保留了专门的传播与防复活机制）；
- 但必须区分两种"删除"：
  - **从你的个人域删除**：你的所有设备都会删掉；
  - **收回别人已经收到的内容**：做不到，也不承诺。去中心化系统里没有一台中心服务器能替你删掉他人设备上已收到的副本，正如寄出的信无法收回。"撤回消息"这类双方约定不再展示，是上层功能，不是物理删除。

### 5. 两个刻意保留的例外

- **消息历史只同步"最近窗口"**，不做从第一句话开始的全量回溯（窗口可配；附件在手机上默认点开才下载、电脑上默认随同步下载，以省流量）；
- **纯本机状态不同步**：每台设备的未读角标各自独立；**身份密钥永不同步**（见 [identity](identity.md)），可对外展示的昵称头像与密钥材料物理分离。

## 数据怎么"存得下来"：副本目标、配额与清理（重点）

Spark 没有云端备份，**你的数据持久性 = 你手里实际有几份副本**。

- **统一副本规则：K=3 目标制**。每份数据的目标副本数为 3：可承载副本的设备 ≤3 台时，K=3 自然等于"每台全量"；设备更多时，三份就够，不必每台都存。K=3 是**目标兼上限、不是保证**——设备不够时系统提醒，不强行处置（与组织 K=3 同一口径）；
- **一个豁免：核心数据始终全量**。结构化记录、消息文本等核心数据体积小，且每台设备渲染界面都离不开它们，故不受 K=3 上限约束、始终全量同步。K=3 管理的是附件、文件这类"不打开就不需要"的大块数据：内容寻址分块，各设备按配额持有子集，打开缺块时 P2P 回补，源设备全离线则如实提示"当前不可用"；
- **配额与清理：驱逐不杀最后副本**。每台设备可为大块数据声明配额（默认 PC 全量、手机按需）；超配额时按"副本数多者优先、最久未用者优先"驱逐本地块，但**域内最后一份副本永不驱逐**——清理永远不会造成丢数据；
- **电脑是主力副本，手机不是**：手机受电量、后台、蜂窝限制，被设计为"只消费、不长期做种"的叶子设备；长期承载副本的是 PC / 家用电脑 / NAS。现实建议：**至少保持一台常开的电脑作为副本源**。注意副本承诺分两级：本节是个人域规则；**组织数据**的 K 副本由成员组织的设备承担（见 [community/membership](../community/membership.md)），手机上的组织数据只是暂存；
- **副本健康度可见**：设置页展示个人域当前副本数与目标的差距，低于目标时提醒，备份引导中如实告知"你当前只有 N 份副本"；
- **身份可恢复 ≠ 数据可恢复（务必区分）**：
  - 助记词 / 备份码恢复的是**身份**（你是谁、你的密钥）；
  - 但**历史数据**（聊天记录、文档、各组织内容的个人侧副本）只存在于设备上。用助记词在一台全新设备恢复后，它是一个"空节点"，历史数据要靠**另一台仍在线、持有数据的自有设备**同步回来；
  - 若所有设备同时损毁 / 丢失、又没有第二副本，那么**即使助记词还在，历史数据也找不回**。这是"无中心备份"的固有代价，产品会在备份引导中明确告知，而不是让用户事后意外。

## 导出与可携带

- 用户可导出个人域全量数据，不被应用锁定；换机迁移的二维码 / 助记词双通道见 [identity](identity.md)；
- 面向"对外证明某段历史"的导出（带存证、可离线核验）属于 [evidence](evidence.md)，不在此篇。

## 边界（这一层不做什么）

- 不做云端备份、不运营任何存储服务器；
- 不在非本人设备上存放个人域数据（组织副本是组织域规则，见 [community/membership](../community/membership.md)）；
- 不做账号之间的个人库互灌——好友关系、组织成员关系都不构成"可读对方个人库"的授权；
- 个人域内是"全有或全无"的完全信任，**不做"对某台自有设备只开放部分数据"的设备级分级**（这是立场而非暂缓）：想要隔离就另开一个根身份——家庭共用设备由每个成员各自的 OS 账号 + 各自的 Spark 实例解决。仅保留消息窗口、附件省流这类类别级裁剪。
